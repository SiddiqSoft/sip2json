# cxxtemplate Documentation Architecture & Standardization Guidelines

This document establishes the official specification, design philosophy, and extraction blueprint for the documentation system across all modern C++ repositories standardized on the [`cxxtemplate`](https://github.com/SiddiqSoft/cxxtemplate) architecture.

---

## 1. Philosophy & Design Principles

1. **Documentation is for Busy Developers**:
   - **Terse & Humble**: Provide immediate, actionable information without condescension or tutorials masquerading as API documentation.
   - **Zero Fluff**: Do not lecture the audience. They are experienced C++ engineers who came to inspect types, function contracts, thread-safety, and exception boundaries.
   - **Authentic Code Snippets Only**: Every example block must be extracted verbatim from live regression tests (`tests/regression/`) or benchmarks (`tests/validation/`) with file and line citations. Never manufacture theoretical or untested sample snippets.
   - **White Space & Hierarchy**: Use clean white space, crisp borders, and distinct typography to separate code, signatures, parameters, return values, and descriptions without redundant horizontal rules or decorative buttons.

2. **Visual Inspiration & Layout Archetypes**:
   - **Home Page**: Two-column, clean, dense layout inspired by [`fmt.dev`](https://fmt.dev/) (hero title, quick example, feature cards, performance highlights).
   - **Getting Started**: Reflect actual build and package managers supported by the project (CMake, CPM, NuGet). If Meson, vcpkg, or Conan are not supported, do not mention them.
   - **API Reference**: OpenCV-style structured layout inspired by [`docs.opencv.org`](https://docs.opencv.org/) (class summary tables, member item boxes with diamond bullets, badges, fully-scoped C++ prototypes, per-parameter tables, explicit returns, authentic test citations).
   - **Related Pages**: Benchmarks (grouped by CPU platform/core count), Architecture, Stream Mechanics, Standards Compliance, Maintainer Guide.

3. **Accessibility & Scaling**:
   - **Pure Relative Units (`rem`/`em`)**: Base font sizing strictly references `rem` to preserve the user's browser scaler and native OS accessibility zoom. Never hardcode fixed pixel font sizes on `html` or `body`.
   - **High-DPI / Retina Desktop Scaling**: Large screens (>= 960px) with device pixel ratios `DPR >= 1.5` (Apple Retina 4.5K/5K, 4K Windows/Linux displays) automatically scale up typography for optimal legibility.
   - **Zero Runtime Scripting**: Sizing, folding, and themes are handled 100% via CSS. No JavaScript font debuggers or layout thrashing.

## 2. Standard Repository File Hierarchy

When `cxxtemplate` is applied to a C++ project, the documentation structure consists of:

```text
<repo-root>/
|-- .azure/
|   |-- az-build-unix.yml            # Shared Linux/macOS build template with doc-build check
|   \-- az-publish-docs.yml          # Multi-platform doc publication pipeline
|-- docs/
|   |-- .guidelines.md               # Standard documentation specification (this file)
|   |-- Doxyfile                     # Doxygen XML extraction configuration
|   |-- hooks.py                     # MkDocs dynamic lifecycle hooks (versioning & pre-build)
|   |-- requirements.txt             # Python doc toolchain dependencies
|   |-- rebuild-docs.sh              # Local build & serve script for macOS & Linux
|   |-- rebuild-docs.ps1             # Local build & serve script for Windows
|   |-- css/
|   |   \-- custom.css               # Centralized typography & theme CSS design system
|   |-- assets/                      # Avatars, logos, favicons
|   |-- quickstart/                  # Getting started, dependencies, package guides
|   |-- api/                         # OpenCV-style markdown API references
|   |-- architecture/                # Benchmarks, async mechanics, compliance
|   \-- maintainers/                 # Maintainer guide & CI/CD architecture

|   |-- generate_api_docs.py         # Doxygen XML -> Markdown OpenCV-style generator

```

## 3. Standard Doxygen Configuration (`docs/Doxyfile`)

Doxygen acts strictly as a headless C++ AST extraction engine to generate intermediate XML (`docs/doxygen_xml/`). It **never** generates HTML, LaTeX, or RTF:

```ini
# Doxyfile - Headless AST XML Extraction
PROJECT_NAME           = "myproject"
PROJECT_BRIEF          = "Library Description"
OUTPUT_DIRECTORY       = docs
INPUT                  = include/myproject
RECURSIVE              = YES
FILE_PATTERNS          = *.hpp *.h
EXCLUDE_PATTERNS       = */tests/* */benchmarks/* */build/*

GENERATE_XML           = YES
XML_OUTPUT             = doxygen_xml
XML_PROGRAMLISTING     = NO

GENERATE_HTML          = NO
GENERATE_LATEX         = NO
GENERATE_MAN            = NO
GENERATE_RTF            = NO

EXTRACT_ALL            = YES
EXTRACT_STATIC         = YES
EXTRACT_PRIVATE        = NO
EXTRACT_PACKAGE        = NO

ENABLE_PREPROCESSING   = YES
MACRO_EXPANSION        = YES
SEARCH_INCLUDES        = YES
BUILTIN_STL_SUPPORT    = YES

QUIET                  = YES
WARNINGS               = YES
WARN_IF_UNDOCUMENTED   = NO
WARN_IF_DOC_ERROR      = YES
WARN_NO_PARAMDOC       = NO
```

### Invariable vs Project-Specific Settings
* **Project-Specific (3 variables)**: `PROJECT_NAME`, `PROJECT_BRIEF`, `INPUT`.
* **Invariable**: All remaining directives are standardized across all repositories.

## 6. API Reference Generator (`scripts/generate_api_docs.py`)

### 6.1 Core Extraction Pipeline
1. Invokes `doxygen docs/Doxyfile` (or falls back to existing `docs/doxygen_xml/` if Doxygen is not in PATH).
2. Parses XML nodes (`<memberdef>`, `<type>`, `<argsstring>`, `<param>`, `<briefdescription>`, `<detaileddescription>`).
3. Generates class summary tables and detailed member item boxes.
4. Generates constants reference tables and error enumeration tables.

### 6.2 Mandatory Parameter Folding Rules
To maintain readability without wrapping failures:
1. **Fold Just After `>`, Never Before**:
   - Closing angle brackets (`>` / `>>`) must strictly attach to the preceding token (e.g. `std::string_view)>>`).
   - Never emit `>` or `>>` on an isolated line.
   - If a parameter name or default value follows (`>> errorCallback = {}`), the fold occurs *just after* `>` on whitespace.
2. **Type Modifiers Attached to Types**:
   - Reference (`&`, `&&`) and pointer (`*`) symbols attach directly to the type:
     - `std::string_view& frameBuffer` (NOT `std::string_view &frameBuffer`)
     - `sipmessage&& parseCallback`
     - `size_t& bytesConsumed`
     - `const char* str`
   - A single whitespace separates the type modifier from the parameter name.
3. **Break on Whitespace**:
   - Line breaks cleanly occur on whitespace following delimiters (after `,` or after `>>`).
4. **Continuation Indentation**:
   - Multi-line parameter names indent at standard continuation indent (8 spaces in prototype code blocks; `param-inner-wrap` in summary tables).

### 6.3 Mandatory Filepath Folding Rules
When code blocks or table cells display filepaths (e.g. in Architecture & Component Relationships tables, include directives, or file maps), paths must fold on the right-most `/` when constrained by column width:
1. **Right-Most Slash Division**:
   - The directory path (everything up to and including the right-most `/`, e.g. `siddiqsoft/private/`) forms the directory segment.
   - The filename and extension (e.g. `sip2json_parser.hpp`) forms the filename segment.
2. **Prevent Breaking Mid-Token**:
   - Both segments are styled with `white-space: nowrap` and `display: inline-block` via `.filepath-dir` and `.filepath-name`.
   - A `<wbr>` word-break opportunity is placed immediately following the right-most `/`.
3. **Responsive Behavior**:
   - If the container/column is wide enough to accommodate the full path, it renders seamlessly on one line (`siddiqsoft/private/sip2json_parser.hpp`).
   - If the path does not fit in the column, the browser folds cleanly at the right-most `/`:
     ```text
     siddiqsoft/private/
     sip2json_parser.hpp
     ```
   - Tokens never break mid-name, mid-extension, or at earlier slashes.
4. **Automated Lifecycle Enforcement**:
   - `docs/hooks.py` enforces this across all rendered HTML via `on_page_content`, transforming inline filepath code spans into `<span class="filepath-dir">.../</span><wbr><span class="filepath-name">...</span>`.

## 7. Dynamic Lifecycle Hooks (`docs/hooks.py`)

The build hook automates pre-build generation and version resolution:

```python
def on_config(config, **kwargs):
    # 1. Resolve SemVer from CI environment or git describe
    version = os.getenv("GITVERSION_SEMVER") or os.getenv("BUILD_VERSION") or "0.0.0-dev"
    config["extra"]["version"] = version

    # 2. Run dependency doc generator
    # 3. Run API reference generator (Doxygen XML -> Markdown)
    # 4. Run benchmark metrics aggregator
    return config

def on_page_markdown(markdown, page, config, files):
    # Replaces {{ version }} and {{ tag_version }} in all markdown files
    version = config.get("extra", {}).get("version", "0.0.0-dev")
    tag_ver = version.split("-")[0] if "-" in version else version
    if not tag_ver.startswith("v"):
        tag_ver = f"v{tag_ver}"
    return markdown.replace("{{ version }}", version).replace("{{ tag_version }}", tag_ver)
```

## 8. Multi-Platform CI/CD Documentation Integration

Documentation build and publication stages must be multi-platform (supporting Linux and macOS runners) and resilient to missing local toolchains:

### Toolchain Detection & Graceful Fallback
In pipeline tasks (e.g. `.azure/az-publish-docs.yml` and `.azure/az-build-unix.yml`), test for `mkdocs` before running:
```bash
if ! command -v mkdocs &> /dev/null; then
    echo "##[warning] mkdocs not installed on this runner. Skipping documentation build."
    exit 0
fi

# Execute strict build
mkdocs build --strict
```

## 10. Step-by-Step New Project Setup Checklist

To integrate this documentation system into a new project in under 5 minutes:

1. [ ] **Copy Architecture Files**: Copy `mkdocs.yml`, `docs/Doxyfile`, `docs/hooks.py`, `docs/css/custom.css`, `docs/requirements.txt`, `docs/rebuild-docs.sh`, `docs/rebuild-docs.ps1`, and `scripts/generate_api_docs.py`.
2. [ ] **Configure `mkdocs.yml`**: Update `site_name`, `site_description`, `site_author`, `repo_url`, and `nav`.
3. [ ] **Configure `docs/Doxyfile`**: Set `PROJECT_NAME`, `PROJECT_BRIEF`, and `INPUT = include/<library_name>`.
4. [ ] **Set Brand Colors**: In `docs/css/custom.css`, customize `--api-primary` and `--api-accent` in the Light and Dark sections.
5. [ ] **Configure API Generator**: In `scripts/generate_api_docs.py`, point to your target XML file and test source paths.
6. [ ] **Verify Local Build**: Run `./docs/rebuild-docs.sh` (or `docs/rebuild-docs.ps1` on Windows) and verify live preview on `http://127.0.0.1:8000/`.
7. [ ] **Validate Strict Build**: Run `mkdocs build --strict` and confirm 0 warnings and 0 errors.
8. [ ] **Commit & Push**: Push documentation files to repository master/main branch.
